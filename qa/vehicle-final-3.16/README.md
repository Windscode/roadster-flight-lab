### 调用依据与结论边界

检视页确实调用 `new RoadsterSim()`，求解器经 `city-data.js` 和 `city-continuity.js` 构造城市碰撞实体。这个依赖是实际存在的。

但在 `frame()`、`frozenArticulation()` 和 `capturePair()` 中，传入检视车模的唯一求解器视觉字段是 `telemetry.wing`。悬架长度、转向与轮胎转角由检视控件明确提供；轮胎接触计数固定为 4，密封裙由开关提供，车体根节点高度为悬架长度减 0.287。检视不把求解器车体的位置或姿态复制给棚内车模，也不载入城市渲染网格。

原拍摄尾翼为 `fixed/0`。`physics.js` 的 `_aero()` 将固定指令交给执行器，再由 `rearWingPose(0)` 给出翼面位置与倾角。车模只用翼面 deployment、position 和 incidence 设置尾翼与支柱；动压、受力和物理车体状态不会改变这里的相机、表面材质或棚光。棚内 Scene、地板、半球／方向灯、程序化条灯环境、HDR 与技术机位均由检视自身创建。

**因此，在记录的固定检视条件与尾翼 0 条件下，没有发现这项远处城市碰撞区间修正进入棚内实际渲染输入的数据通路。** 这是可审查的源码与数据流推论。它不等于整个静态闭包同字节，不证明 32 张 PNG 与最后构建逐像素相同，也不把原图改称为 `81926…` 新拍。

以下均排除在该推论与原组件记录之外：原主城驾驶座舱图、全部独立 UI 截图、最终城市行驶／导航、逐 draw／14 帧覆盖、城市烘焙体积及其像素贡献、硬件性能与显存、网站公开身份。主应用 HUD 和城市已变更，必须使用各自的最后状态证据。
