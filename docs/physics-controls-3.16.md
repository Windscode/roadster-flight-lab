## 1. 输入、控制权和姿态的证据链

3.15 源码中 KeyX 已映射到 roll，松开 X 也不会取消已接受的动作。实机截图间隔不能排除一个约 3.7 s 动作已经完成，因此没有把“短按后未看到动作”定性成求解器不执行 X。应用事件层的文本编辑/界面占用/暂停路径需要给出明确回执；本轮主集成把这些状态与物理预检查分别记录。物理层 `startManeuver()` 保存 accepted/rejected 及当时原因，执行中的 phase、实际角行程、峰值重心、起止时间和气源账单在 `_maneuver` 清空后仍可读。终态汇总包含最后积分步，避免在决策时刻提前冻结最后一小段角度和气量。

城市、静止轮胎承载、350 bar bench、无风无故障的数值输入回归，在 KeyX 按下后 100 ms 发出 keyup：动作于 3.691667 s 完成，峰值重心 3.898734 m，实际滚转行程 361.179504°，外供 150.172655 kg，瓶装气消耗 0 kg。它验证 release 不取消原快速动作及结果可追查，不构成用户电脑原生按键验收；终态是原动作“承载着陆”判定，也没有擅自加长为慢而高的表演。

### 原生 X：触发结果与短沿时序分开验收

完整旧 3.15 对照站（原构建 `0ca13961…`）实际收到一对 trusted X 事件，原应用将 keydown 记为 `accepted=true / reason=action`。采样看到了 rotate、land 阶段，最后返回 DRIVE 并由四轮承载。该次 `keyboard.press('x', {delay:50})` 的 50 ms 是工具参数，不是实际按住时长；原始记录给出以下不同计时口径。

| 口径 | keydown → keyup 间隔 | 能说明什么 |
| --- | --- | --- |
| 工具请求的 delay | 50 ms | 请求值；原运行没有记录两次实际 API 调用时刻 |
| DOM `event.timeStamp` | 999.600 ms | 浏览器创建两个事件时的时间戳间隔 |
| QA 捕获阶段回调 `observedAt` | 1142.700 ms | 页面实际执行只读观察回调的间隔 |
| InputSession `wallTimeMs` | 1142.500 ms | 生产应用记录两次事件的间隔 |

因此该次是原 X 触发与运动阶段证据，不能标成 50 ms 短按通过，也不能由截图推定完整无碰撞滚转。旧 3.15 的 X 不启动原来仅由 E/Q/1/2 触发的物理时序窗口，零条留存物理样本不代表零接触。原报告、压缩时序和三张原图字节不变，计时说明另附。[旧版范围补充及逐文件哈希](../qa/native-controls-3.16/baseline-requested-50ms-delayed/scope-addendum.json)

本机 Playwright 1.62.1 的实际源码显示：`press` 先等待 keydown 的协议回复，再等待 delay，最后发送 keyup。修订的 QA 脚本先设独立 Node 50 ms 定时器，然后发送 down；up 无须等待 down 回复。单独 down/up 的客户端请求、服务端请求控制器及 Chromium 消息 ID 分开等待各自回复，不共享前一个按键的完成条件。无浏览器的源码调度自检使用本机真实 Keyboard 类，让 down 回复保持未完成直到收到 up；实测两次 API 调用间隔 50.013 ms。原 `press` 类在 150 ms 的模拟 down 回复延迟下，到约 201.826 ms 才调用 up。这只证明工具调度差异，不证明真实浏览器已经按时交付事件。

最后原生脚本对正常 X、复位暂停后的 X、菜单拒绝中的 X 均保存 Node 调用／回复时刻、DOM 时间戳、页面观察时间、生产应用接收和动作回执。短沿条件预先声明为有序 trusted down/up，且 API、DOM、观察回调三种间隔分别大于 0、至多 100 ms；每项保留实测值，不称精确 50 ms 或硬件键盘认证。应用接收／动作接纳另行判定，繁忙页面的观察延迟本身不构成 X 功能故障。完整但过慢的一对按键仍继续观察动作和后续独立操控，最终报告保留 `short-timing-not-confirmed`；不会用运动完成掩盖时序未确认。运行前后实际服务器源码／光场和 QA／工具链哈希分别核验，旧版不受无关的本地候选源码变化误判。[原生脚本及无浏览器自检入口 `--check-x-scheduler`](../scripts/native-controls-3.16.mjs)

## 3. 台阶接触：修复了什么，仍缺什么

旧悬挂支撑只从轮心向车体下方打射线：轮胎前缘已经碰到台阶棱边时，轮心射线仍落在下层地板，不能及时提供边缘支撑。之后刚性轮胎止挡突然接触，冲量与后续翻覆对步长极为敏感。新支撑查询对连续胎冠包络与静态盒子的 6 个面及 12 条真实边解析求交，得到最早可支撑的悬挂长度、实际离轴接触点及三维法向；已有 3.15 轮碰撞朝向同步继续保留，新支撑查询使用相同实际转向。独立解析式 `中心高度 = 台阶高度 + sqrt(R² - 轴前缘距离²)` 对 10/20/30 cm 轴前偏距逐一验证，30 cm 时仍应由下层地面支撑的负例保留。

### 整轮回归中发现并修正的连续接触斑缺陷

首个 3.16 接触实现使用同半径的中心/左右三处圆截面并取最早命中。极小侧倾就把整个支撑力作用点从中心跳到 ±132.5 mm 外缘，产生不连续滚转力矩，继而在直线制动时放大微小航向扰动。四轮始终承载、没有刚体碰撞、没有微步细分，所以原因已从制动停不下来、碰撞法向错误及微步调度中分离。原三截面查询与当时完整轮胎力计算过程被逐字冻结，配对加载同一完整初始快照，旧失败继续实际执行并保留轨迹。
