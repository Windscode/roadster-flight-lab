## 1. 车身条纹：修正已复现的阴影机制，保留进一步隔离

### 已确认的机制与尚未确认的因果

本地 Three.js 的 PCF soft 阴影核在多个不同纹理坐标取深度，但全部用中心接收点的深度比较。对于斜面，相邻 texel 的实际深度本来不同；当表面斜率和阴影 texel 尺度超过小偏置的补偿量时，没有任何遮挡物也会出现周期性自遮蔽。这个机制已经用独立的无遮挡平面条件复现。

它能解释规则条带的一条形成路径，**尚不能证明用户图中所有条带都是 shadow acne**。法线、曲面分段、高光和玻璃排序仍须同机位隔离图确认。特别是旧模型前肩的几何起伏与密集阴影条带应分别判断。

### 具体修改

[`receiver-plane-shadows.js`](../dist/receiver-plane-shadows.js)在阴影坐标求局部接收平面的深度梯度，对每个 PCF 样本按实际最近 texel 中心修正比较深度。方向光和聚光灯均接入；透视聚光坐标也先进行透视除法。梯度在片元入口、灯光条件分支之前求取，避免把导数计算放进不一致的光锥分支。

城市在 `city-environment.js` 的材质编译链末尾接入；车辆检视给当前车、按需载入的历史车和地面材质接入同一函数。没有增加阴影纹理采样、灯数或阴影图，也没有改主光强度、相机曝光、车漆反射或物体 `castShadow`。既有法向和深度偏置保留：检视图 2048²、8 m 覆盖、normal bias 2.5 mm、depth bias −0.00008；城市沿用随 texel 尺度调整的偏置。改动补偿取样位置差异，而非把接收面大幅移离阴影。

同条件数值例为 1536² 阴影图、投影深度梯度 `[0.067, 0.042]`、中心深度偏置 −0.000043，遍历 6,400 个亚 texel 相位。这里的正确答案由场景条件给出：无遮挡平面应完全可见；在前方加真实遮挡面则应被挡住。

| 相同平面条件 | 原中心深度比较 | 接收平面校正 |
| --- | ---: | ---: |
| 无遮挡平均可见比例 | 0.801532 | 1.000000 |
| 无遮挡最小 / 最大可见比例 | 0.740358 / 0.883293 | 1 / 1 |
| 加深度差 0.002 的真实遮挡面 | 0 | 0 |

这是阴影取样机制的数值验证，数值不是实际车漆亮度或截图改善百分比。局部一阶平面对轮廓、深度突变和强曲率仍是近似；需要实际像素检查过度补偿、阴影接触和边缘漏光。

### 同机位七项隔离

检视入口支持 [`?view=front-lamp`](../dist/vehicle-inspection.html?view=front-lamp)，界面新增“条纹与曲面隔离”。“导出同机位七项隔离 ZIP”在同一选中模型、相机、LOD、悬架、转向和尾翼状态下采集：

1. 完整材质，接收平面校正开启。
2. 完整材质，校正关闭，复核原阴影比较。
3. 仅关闭车体接收阴影，投影仍保留。
4. 关闭环境贡献，保留局部灯和实际几何。
5. 纯漫反射灰模，继续保留接收平面校正。
6. 视空间法线。
7. 三角网格。

每次实际绘制之后立即按 drawing buffer 原尺寸复制，并冻结该帧条件；七次复制结束后才开始异步 PNG 编码。八个文件为七张未经缩放或标注的 PNG 加一份 JSON，共用 `captureId`。界面输入、相机、物理刷新与 resize 在事务期间冻结，结束后恢复；所有隔离都可逆，不改变几何、姿态、物理或默认显示。无环境模式也同步当时的玻璃/剖视状态，不使用过期材质克隆。

`surfaceDiagnostics` 元数据记录隔离模式、校正开关、阴影图尺寸和偏置。`?surface=no-shadow`、`?surface=normals`、`?shadow=legacy`可作为直接诊断入口。现有“3.9 / 当前”几何对照仍使用当前同一渲染器；冻结历史模型不等于完整历史阴影流水线。灰模、无环境与法线改变了明确列出的渲染分量，应作为机制隔离，不计入默认成品 A/B。

## 2. 夜间远灯：从亮灯壳走到静态表面直接受光

### 已确认的缺口

3.9 原来已经把**相机位置**传给灯池。3.10 又改进了实际照射覆盖评分、视线方向、滞回和淡变；本轮没有把“车中心改相机中心”重复说成新修复。

但 3.10 夜间离线场只含一次反射后的漫射光，特意排除了灯具直接光。远处可见灯具退出有限实时灯池后，其灯壳仍发光，相应静态路面和建筑却失去了该灯的直接受光项。仅改善灯池选择或增加小量环境填充不能完整补上这个结构性缺口。

### 新直接场与重复计数处理

[`night-direct-transport.js`](../dist/night-direct-transport.js)使用场景中实际作者定义的灯具位置、方向、强度、有限范围、光锥和 penumbra，沿灯具至探针的路径检查静态遮挡，再保存六方向直接漫射照度。发光但未登记为照明的招牌、车辆和车灯不进入该场。数据写到独立 `assets/night-direct-irradiance`，保留原日间间接光和夜间一次反射场。

[`night-direct-lighting.js`](../dist/night-direct-lighting.js)只接入静态城市材质。按表面到真实相机的距离，用 `smoothstep(12 m, 28 m, distance)` 混合：近处保留实时街灯漫射；远处由静态直接场接管。在实时聚光灯执行后只缩减已选**街灯**产生的漫射增量，再加入对应权重的静态场。车灯不缩减，实时高光保留，车漆整体仍由动态光照负责。

因此静态直接光不是简单叠加到同一盏实时灯之上。淡入、换灯和静态场仍使用各自明确职责；实时池之外的场不随车或相机移动而换烘焙身份。高空 24–32 m、全城 x/z 外边 600–624 m 平滑退场，与实际外层探针边界一致，越界后恢复完整实时贡献。不会在 32 m / 624 m 硬边上突然扣掉实时漫射。

这是两种有不同源覆盖率的照明近似之间的互补过渡，不是完全一致的光照分解。12–28 m 过渡带仍需真实移动检查；近处实时区域保留车辆动态阴影，远处静态场不含车体遮挡。道路可由直接灯照亮，不再依赖镜面倒影代替路面受光；桥下朝下的面主要仍依靠已有反射光和环境填充，不能把新增直接场说成完整桥底多次 GI。

### 数值与预算

同一城市几何身份 `9b8c5ef0d7f94adba2ee9155d7a1565bffa48ade384dacb940bcbc2b3d4a6fff`，同一灯锚点身份 `6c4ed39f5742a23f7e7682654c3d894fdaaa8b2c56f33380e6e65209cc34f241`。以下为朝上法线的**直接场线性 RGB 量**，不是测得照度或显示器亮度。此前退出实时池时该灯具直接项为零，已有反射光、环境光并非零。

| 探针坐标 m | 新直接场 RGB | 被静态结构遮挡的候选灯路径 |
| --- | --- | ---: |
| `[-200, 0.6, -344]` | `[11.5947, 6.7251, 3.3720]` | 0 |
| `[-200, 0.6, -279]` | `[22.4552, 15.3694, 9.8833]` | 2 |
| `[-203, 2.4, -264]` | `[3.1920, 2.5927, 1.8597]` | 2 |
| `[-138, 0.6, -398]` | `[8.5327, 5.8026, 3.1948]` | 0 |

独立的白色点灯轴线条件还核对了有限范围的反平方衰减、向下法线零值、有遮挡为零及无灯为零；实景有遮挡输运从不大于相同条件的无遮蔽计算。移动相机并把车留在别处，烘焙身份不变；切回晴天禁用夜场。

独立复核还修正了直接场的重复高度退场：原组合在 24–32 m 过渡中为 `(1-h)+h²`，等能量输入在 28 m 得到 0.75；现在统一只退场一次，为 `(1-h)+h=1`。175 个代数位置和实际注入表达式已纳入回归。这是权重公式修复，不能解释成实测立面亮度提高 25%；灯具强度、曝光和原 bounce 场没有改变。

新增二进制共 **3,334,320 B**，加原夜间反射场总计 **6,668,640 B**。每个场在稳定区最多读三个方向，网格过渡区最多六次三维纹理采样；新增场不增加实时灯和阴影图。路线水平间距为 high/ultra 4 m、balanced 8 m，外围 24 m，高度为 0.6 / 2.4 / 6 / 12 / 26 m，最大纹理维度不超过 256。发布多一个离线场并非 GPU 成本为零，实际帧时待测。

烘焙的静态遮挡采用现有闭合物理包络，不是逐门框的光照贴图。细小立面退进、灯光边缘和静态阴影会被插值软化；可能出现窄处漏光，须用近、中、远和桥下画面检查。新场身份、各二进制 SHA 与完整输入见[烘焙报告](../qa/night-direct-bake-3.11.json)。原 3.10 日间与夜反射二进制未被重新生成或覆盖。

## 3. 材质、曲面与街区复核结论

源码分类并非“所有材料都是金属”：当前混凝土 metalness 为 0、roughness 约 0.90；干沥青粗糙度范围 0.72–0.96。3.10 已把湿膜约 0.43–0.61 与积水约 0.105–0.18 分开，并保留有限投影/剔除的平面反射。用户旧图中反射主导、暗表面不可读的观感确实存在，但不能从该观感反推所有 material 的 metalness 都错误。

本轮选择修复静态直接照明的缺项，让这些已有非金属表面具备受光结构；没有通过把所有反射关掉解决。新灯场下玻璃、车漆、湿膜、积水的相对亮度还未做真实画面对照，镜面泛滥的最终观感验收仍开放。

车辆以附件 Tesla 当前官方楔形、硬折线外形为准，前悬、后悬、座舱、肩线、轮拱和灯组的既有地标分析继续适用。官方摄影内参未知，项目轮距、轴距、喷口等都是工程重建假设，不是原厂 CAD。新阴影比较不会将机盖折线改圆，也不会改变悬架、轮胎、碰撞或物理尾翼。

## 4. 验证结果与后续图形验收

[`visual-regressions-3.11.json`](../qa/visual-regressions-3.11.json)记录上述独立阴影 oracle、诊断状态往返、七帧事务和直接灯场验证。七帧测试使用合成画布标记字节验证冻结顺序及 ZIP 绑定，明确**不是渲染图**。

[`city-shaders-3.11.json`](../qa/city-shaders-3.11.json)使用本仓库真实 Three `WebGLProgram` 展开 include、CSM 修改和 unroll 后的输出，在已有 glslang 编译器检查 **92 对 / 184 stages**：城市三档、晴天/湿夜、普通/实例化材料，普通 PBR、clearcoat、道路、铺装、混凝土/玻璃/珐琅、检视独立阴影和灰模路径均通过兼容编译。编译器把 stock Three 函数名 `average` 视为保留冲突，因此仅在临时编译输入重命名为 `roadsterReviewAverage`；原始诊断和兼容结果均保存，生产 vendor 没改。它不是未经兼容处理的 92 个 exact pass。

验证还检查展开后的**实际调用**：夜间 balanced/high/ultra 的聚光阴影分别有 3 / 5 / 6 个 `roadsterGetShadow` 调用（含车灯），以实际 `vSpotLightCoord` 接线；不是只检查补丁源码里出现了函数名。日间方向光路径、检视单个主光路径同样核对。此结果不包含目标浏览器 ANGLE/驱动或实际 framebuffer，所以 X3595 / X4000 是否在目标设备消失、是否有可见变化仍不能由此宣称。

实际后采应继续遵守原[证据计划](visual-evidence-3.10.md)，版本标为 3.11，补充：

- 车辆前灯、前四分之三、正侧各导出七项隔离 ZIP，条灯与自然光各自成组；默认完整材质中比较校正开关，再检查无阴影、无环境、法线和网格中的条带是否保留。
- 城市 01 织桥、02 交换厅、03 桥下、04 横街、05 南岸固定机位，1280×720 实际 drawing buffer、高画质、相同 DPR、相机、车辆状态和曝光，预热至少 3 s 后导出真实 PNG/同次条件。2031×1244 另成组。
- 固定相机与车分离、暂停相机转向、沿路移动跨越 12–28 m 过渡，检查受光范围、灯池淡变、远处道路直接光、阴影接触、玻璃/湿路闪烁；全环线含横街和机造大道，不能只看织桥入口。
- 运行相同路线时区分加载、5 s 预热、连续驾驶、暂停；报告帧时 p50/p95/p99、长帧、实际可取得的 GPU 标识与 query，可用性未知则保留未知。

尚未取得或通过的项目是：3.11 同条件真实车体条纹与曲面后图、夜景暗部及镜面观感、光池/过渡运动稳定性、目标 GPU shader 日志、实际路线帧时、完整远景与城市边界设计。当前实现为这些问题提供了可操作修复和可重复采集入口，不删除未完成的图形验收要求。
