# 3.18 运行阴影：原生连续片段与验收边界

本轮保留了真实键盘驾驶、转向、相机拖动和昼夜切换的 WebM 与逐显示回调状态。**原生观察支持新调度在实际应用中运行，但没有把软件渲染器上的短片判成“所有阴影闪烁都已消失”。** 更直接的修复证据来自冻结 3.17 模块与当前模块的灯光/阴影相机时序对照；它与本文件的实际画面记录分别说明机制和运行表现。

## 1. 真实来源与输入链

使用已有项目的 `qa/native-shadow-motion-3.18.mjs`，在本机两个独立端口分别载入冻结 3.17 和本轮开发源。源文件响应逐一计算 SHA256，同时保存 `model-build.js` 当次实际声明。候选记录有不同阶段身份，未用最后的版本值回填截图或录像。

| 片段 | 当次真实构建 |
| --- | --- |
| 全部 3.17 基线片段 | `26692f4324d2392ae7ac5981709299e2f6da29929259221445a7ba49591781d4` |
| 候选实验室 | `c0802f8d54ef25c4907716e824cd294e0d91edbbcc5ed947622b5dfde51f5bec` |
| 候选城市 | `29f7f7049d4dcfc115026042e11bb8d8a2b42a61abbcefbc8cd8817e3d9a0189` |

随后控制入口又有独立修改，这两个候选录像均保留阶段身份。两段候选实际加载的阴影调度、城市环境、车灯和车模源 SHA 在汇总中分别列出；相同专项源不等于整个构建相同。基线对应仓库完整历史 `d9a4fbfd434fe49cdbeae18c32f624360e9dc4e9`，用户本人运行的 build 仍未核实。

真实键序为 W 直行→保持 W 追加 A→松 A 追加 D→松 D/W→拖动相机。实验室随后按 C 并松键观察；城市通过正常天气选择器切湿夜，再按 W、追加 A、松键并按 C，最后切回晴天。每个片段内部从同一运行状态连续推进，没有向求解器注入位置、速度、姿态、接触或模拟步。灯光为 UI 的随天气模式，天气选择和曝光按钮使用原事件链，未关闭阴影或调用受保护控制接口。

实验室实际画布为 800×450、高档，城市有界重试为 640×360、高档，DPR=1。城市晴天采用原曝光基线 0.87，湿夜按钮目标为 1.02；这两个值随明确天气操作改变，不能把天气切换造成的明暗变化当作随机闪动。冻结基线的夜间曝光按钮随后超时，只记录到 0.87 下的一次夜态观测，因此夜间并没有形成同曝光的完整双版本动态对照。

每次相机截图有前后独立状态读取，但没有声称与 framebuffer 原子绑定。rAF 记录也只是应用报告的显示调度与公开状态，并非 GPU 深度图读回。原始模拟时钟、位置、姿态、轮转角/悬架、实际输入、相机模式、天气、曝光、renderBudget、接收到的输入 journal 和源码响应都保留。

[汇总与每段源身份](../qa/shadow-native-3.18/summary.json) 链接到各段原始 `report.json`、压缩时序和 WebM。视频以原生墙钟时间记录，加载、设置等待和重复 compositor 帧都保留；容器编码 25 fps 不能读作应用以 25 FPS 运行。实验室驾驶末段接近并接触端墙，车辆轨迹没有为取得“干净画面”重新归位。两个版本的真实进度、转向结果和相机操作时刻存在差异，不构成配准后逐像素 A/B。候选城市白天 W 阶段为 0.983/目标 1.000 模拟秒，湿夜 W 阶段为 0.642/目标 0.800 模拟秒；各自触及 35 秒墙钟上限。没有为写成通过而补模拟步或延长该阶段限时。完整城市录像含约 40 秒加载/设置，因而长于 360 秒的活跃协议预算。

保留的失败包括：第一次启动缺少录屏 ffmpeg 路径；城市 800×450 在焦点定位时超过 15 秒；冻结 3.17 的 640×360 连续驾驶成功进入湿夜后，下一次曝光按钮 locator 超过 15 秒。前者使用环境中已有 ffmpeg 路径修复；后两者使 QA 的原生 DOM 聚焦/按钮操作合并到有界事件调用，产品源码未因此改变。原失败录像、日志和旧执行器快照均保留，没有删除失败再仅交成功重试。

实际控制台还记录本地 `deployment.json` 404、未附 URL 的资源 404、SwiftShader 不支持 `KHR_parallel_shader_compile` 的告警；昼夜环境处理可能记录滤波样本截断告警。它们逐段列出，不能声称 console 全空。没有发生故障的阶段与有界超时的阶段分开报告，不以条目数或是否写出 JSON 代替验收。

## 3. 阴影来源的区分

| 来源 | 实现与本轮证据 | 仍然不能推论的内容 |
| --- | --- | --- |
| 法线/材质纹理 | 保留法线贴图、材质采样器和自阴影接线；`receiver-plane-shadows.js` 前后 SHA 相同。主形体修改会改变真实几何法线，所以整车图不是只换阴影算法的隔离对照 | 不能用一张工坊静态图排除全部运动高光/纹理混叠 |
| 头灯深度图时序 | 冻结旧模块在 120 Hz 连续显示位姿中，灯具更新但深度相机节流；三档分别 203/197/189 个过时帧，最大相机位置差约 1.00/0.85/0.68 m。当前同序列为零 | 这些是实际 Three 相机矩阵计算，不是 GPU 以 120 FPS 跑过的声明 |
| 车体/车轮、物理与插值显示 | 当前运动深度失效与显示车体、转角、悬架及相机变化使用同源姿态。原生记录可读到 motion/updated 状态 | 调度标志没有直接测量每个阴影像素；旧版缺少新 motion 字段不能记成“车没运动” |
| 实验室投影游移 | 固定光方向，并按实际阴影 texel 对齐投影原点；保留原分辨率与 normal bias | texel 对齐不能消除有限分辨率的所有边缘跳变 |
| 城市日光级联与夜间实灯 | 原生高档晴天实际为两层 1536 阴影；夜态保留实灯/头灯投影和湿路反射。候选切换连续推进，没有冻结成图 | 云端慢帧不能覆盖用户快速转头、接近级联分界和高帧率驾驶的所有组合 |
| 曝光与真实光照切换 | 天气/曝光操作及各帧数值保留；白天阴影与湿夜头灯是不同照明条件 | 切换的正常明暗变化不能算成同一类随机闪烁，也不能拿切换后单帧证明稳定 |

[机制原始报告](../qa/shadow-motion-3.18/report.json) 对应真实冻结旧模块，保留同序列、矩阵和原源哈希。原生实验室的软件回调中位间隔约 238 /287 ms，城市重试更慢；这样的低显示速度本来就可能让旧版阴影节流每次都有机会更新，不能据此认定旧代码无故障。新增同显示帧更新还可能增加真实 GPU 工作量，不能用云端速度反推用户帧时。

## 4. 人工看图范围与后续边界

实际查看了实验室三张截图/版、多个提取视频帧，以及城市原始截图和有限视频帧。白车在驾驶和转向的提取帧中有实际车体材质、阴影与接地关系，实验室地面的高频细纹依然可见。湿夜 265 秒车身被暖色灯池照亮，285 秒镜头被前景柱体部分遮挡，310 秒不同位置的车身较暗。没有进行可以从运动、灯池、反射与遮挡中分离出阴影时序的逐像素分类，不能把这些稀疏帧的亮度变化自动判断为正常或故障。画布小、车身只占部分像素、显示回调慢，也不能排除细小闪烁或时间混叠。

本轮候选城市三张原图：[移动前](../qa/shadow-native-3.18/candidate-city-small/01-before-motion.png)、[白天转向与相机后](../qa/shadow-native-3.18/candidate-city-small/02-after-day-turn-camera.png)、[湿夜近灯与松键后](../qa/shadow-native-3.18/candidate-city-small/03-night-headlamps.png)。基线 [录像末尾实际夜态](../qa/shadow-native-3.18/baseline-city-small/video-frames/wall-210p8.png) 与候选 [录像中回到晴天](../qa/shadow-native-3.18/candidate-city-small/video-frames/wall-380.png) 也已查看，二者仅说明对应状态确实呈现到画面。完整抽帧时间和人工复核范围见汇总，不声称完整录像已在高刷新率设备上回看。

用户设备的连续移动/转角、日夜、快速相机和高/极高档位仍没有在本轮原生软件片段中得到等效覆盖。当前结论是**具体时序与投影问题已修，有限原生连续证据已保存，用户所述运行体验尚不宣称全面关闭**。静态形体图、控制动作完成回执、应用导出成功、某一帧的 draw call 数均不替代这一边界。
